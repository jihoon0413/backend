# confirm 최종 분석 - 현실적인 PG 지연 기준 (2026-10-11)

지금까지 WireMock "정상" 시나리오를 `fixedDelayMilliseconds: 50`(50ms 고정)으로 썼는데, 이건 실제 PG 승인 API치고 비현실적으로 빠른 값이다. 국내 카드 PG 승인 API는 보통 네트워크 왕복 + 카드사 승인까지 포함해서 수백 ms~1~2초대로 알려져 있다(**이 숫자는 Toss Payments의 공개된 실측 벤치마크가 아니라 일반적인 카드 PG 승인 API 경험치를 바탕으로 한 가정값**이다 - 정확한 수치가 필요하면 Toss 샌드박스에서 직접 측정하거나 운영 로그를 보는 게 맞다).

그래서 "정상" 시나리오를 **median 700ms, sigma 0.35짜리 lognormal 분포**(WireMock `delayDistribution`)로 바꿔서 매번 같은 값이 아니라 실제처럼 흔들리게 설정하고 재측정했다. "장애" 시나리오(8000ms 고정, PG 전체 장애 재현용)는 그대로 유지.

## 실행 조건

- 아키텍처: Outbox+Kafka 분리 1~3단계 전부 적용된 상태 (요청용/통지용 relay 분리, 병렬 발행, confirm 전용 컨슈머 10개 × 파티션 10개)
- WireMock `/brandpay/payments/confirm` 스텁:
  - **정상**: `delayDistribution: {type: lognormal, median: 700ms, sigma: 0.35}` → 실측 샘플 0.40~1.07s 범위로 확인됨
  - **장애**: `fixedDelayMilliseconds: 8000` (고정, PG 전체 다운 재현)
- k6(`facade-isolation-test.js`): `CONFIRM_RATE=20 CONTROL_RATE=20`, 정상은 `DURATION=30s`, 장애는 `DURATION=60s`
- 완료시간은 두 가지로 잡음: ① k6가 `/status` 폴링으로 재는 값(`confirm_completion_duration`, 폴링 주기만큼의 측정 오차 포함) ② DB 타임스탬프로 직접 재는 "진짜" 백엔드 지연(`payment_request_outbox.created_at` → `payments.updated_at`, 측정 오차 없음) - **②가 진실에 더 가까우니 ②를 기준으로 판단할 것**

## 새로운 발견 - "정상" 상황인데도 완료시간이 왜 이렇게 느린가

PG가 median 0.7초로 정상 응답하는데도 완료시간 p95가 6초나 나온 건, **지금 confirm 전용 컨슈머 워커가 딱 10개로 고정**돼 있는데, 이게 `CONFIRM_RATE=20/s` 부하를 받치기엔 용량이 모자라기 때문이다.

대기열 이론으로 보면: 워커 10개가 "동시에 처리 가능한 최대 건수"인데, 초당 20건이 들어오고 건당 평균 처리시간이 ~0.9초(네트워크 오버헤드 포함)면, **평균적으로 동시에 필요한 워커 수 = 20 × 0.9 ≈ 18개** - 10개보다 많다. 즉 **장애가 아예 없어도, 이 부하 수준에서는 워커가 만성적으로 부족해서 대기열이 쌓인다.** 이건 장애 복원력 문제가 아니라 순수 **용량 설계(capacity planning) 문제**다.

워커 수(10)는 애초에 "Kafka 파티션 수와 맞춰야 concurrency가 의미 있다"는 이유로 10으로 정했을 뿐, 실제 처리량 요구치를 계산해서 정한 값이 아니었다 - 이번에 현실적인 지연으로 다시 재보고서야 드러난 설계 공백이다.

**결론**: 지금 측정한 confirm 수치들은 "격리(Tomcat에 영향 안 줌)"는 완벽하게 증명하지만, "충분한 처리량(완료가 빠름)"까지는 아직 증명 못 했다. 워커 수를 늘리거나(예: 20~25개, 파티션도 맞춰서), 혹은 `CONFIRM_RATE` 기준치를 재검토하는 작업이 다음 단계로 필요하다.

## 지금까지 발견한, 서로 다른 성격의 지연 원인 3가지 정리

| 원인 | 해당 구간 | 해결 상태 |
|---|---|---|
| ① PG 자체의 실제 응답시간 | 장애 시나리오 PAID 16건의 8.75초 | **해결 불가** - 외부 의존성의 물리적 하한선 |
| ② Outbox relay 처리량 한계 | 접수→Kafka 발행 지연 (원래 ~7~8초) | **해결됨** (1~3단계: 배치/주기 조정 → 병렬 발행 → relay 분리) |
| ③ 컨슈머 워커 풀 용량 부족 | 정상 상황에서도 완료시간이 PG 지연보다 훨씬 늘어짐 | **미해결** - 이번에 새로 발견, 워커 수 재설계 필요 |

## TimeLimiter란?

**resilience4j의 네 번째 보호장치**(CircuitBreaker/Retry/Bulkhead와 같은 패밀리) - **"이 호출이 N초 안에 안 끝나면 강제로 실패시킨다"**는 역할만 하는 간단한 컴포넌트다.

### 왜 필요한가 (지금 코드의 빈 구멍)

지금 `confirmBrandpay()`에는 `@CircuitBreaker`만 있다. CircuitBreaker는 **호출이 끝난 뒤에야** 그 결과(성공/실패/느림)를 집계해서 "앞으로 열지 말지"를 판단하는 거라, **지금 진행 중인 느린 호출을 중간에 끊어주진 못한다.** 그래서 WireMock이 8초를 기다리게 만들면, 그 요청을 처리하는 워커 스레드는 CircuitBreaker가 뭘 하든 상관없이 **고스란히 8초를 묶여있는다.** 이게 지난 답변에서 본 "UNKNOWN_HOLD인데도 몇 초씩 걸리는" 현상의 근본 원인 중 하나 - CB는 사후 조치만 하고, 진행 중인 느린 호출 자체를 끊는 장치가 없었다.

### 동작 방식

```java
@TimeLimiter(name = "brandpayTimeLimiter", fallbackMethod = "confirmBrandpayFallback")
@CircuitBreaker(name = "brandpayCircuitBreaker", fallbackMethod = "confirmBrandpayFallback")
public CompletableFuture<PaymentConfirmResponseDto> confirmBrandpay(...) {
    return CompletableFuture.supplyAsync(() -> tossFeignClient.confirmBrandpay(...));
}
```

- 호출을 별도 스레드(또는 Future)로 실행하고, 설정한 시간(예: `timeout-duration: 3s`) 안에 안 끝나면 그 Future를 취소하고 `TimeoutException`을 던진다.
- **중요한 제약**: TimeLimiter는 비동기 반환형(`CompletableFuture`, `CompletionStage` 등)에만 적용된다 - 지금처럼 동기 메서드 그대로는 못 쓰고, 메서드를 `CompletableFuture`를 반환하도록 바꿔야 한다. (내부적으로 별도 스레드에서 실행해야 "취소"라는 개념이 의미가 있기 때문)
- Toss가 실제로 8초 뒤에 성공 응답을 보내더라도, 이미 3초에서 타임아웃으로 끊겼으면 그 뒤에 Toss가 보낸 응답은 그냥 버려진다(Future가 이미 취소됨) - **"느릴 수도 있지만 성공할 수도 있었던 요청을 강제로 실패 처리한다"는 트레이드오프**가 분명히 있다.

### 지금 상황에 적용하면 뭐가 좋아지나

- 워커가 8초씩 묶이는 일이 없어진다 → ③번 원인(워커 풀 용량 부족)의 영향이 줄어든다(워커가 더 빨리 반환되니까 같은 10개로도 더 많은 요청을 받칠 수 있음)
- UNKNOWN_HOLD로 빠지는 요청들의 지연 분포(0.04~12.49초)에서 긴 꼬리가 사라지고 "타임아웃 설정값(예: 3초)" 근처로 모일 것
- 반대로, 장애 상황에서 PAID로 성공했을 16건 중 일부는 **"8초보다는 느렸지만 결국 성공했을 텐데 3초에서 강제로 실패"** 처리될 수 있다 - 성공률이 약간 떨어질 수 있음

### 어떤 timeout 값을 줘야 하나

지금 서킷브레이커의 `slowCallDurationThreshold: 3000ms`랑 맞춰서 TimeLimiter도 3초 정도로 주는 게 일관적이다 - "3초보다 오래 걸리면 느린 호출로 치겠다"는 기준을 CB와 TimeLimiter가 같이 쓰는 셈. 다만 정상 상황(이번에 잰 median 700ms, p95 체감상 1~2초대)을 고려하면 3초는 넉넉한 값이라 정상 요청을 잘못 끊을 위험은 낮다.

## TimeLimiter 적용 결과 (2026-10-11 추가)

`TossBrandpayApiClient.confirmBrandpay()`를 `CompletableFuture` 반환형으로 바꾸고 `@TimeLimiter(timeout-duration=3s)`를 `@CircuitBreaker`와 같이 적용했다. 실제 호출은 전용 풀(`tossCallExecutor`, 20~30개)에서 돌고, 3초 안에 안 끝나면 `TimeoutException`으로 강제 종료된다. 단일 호출로 직접 확인: 8초 지연 상황에서 **3.485초**에 끊기는 것 확인(기존엔 8초+ 대기).

### 장애(8초 고정 지연) 재측정

| 지표 | TimeLimiter 전(3단계까지) | **TimeLimiter 후** |
|---|---|---|
| 완료시간 avg(k6) | 4.11s | **2.82s** |
| 완료시간 p95(k6) | 10.69s | **5.74s** |
| accept p95 | 378.75ms | 422.66ms |
| control_traffic p95 | 91.91ms | 371.23ms* |
| Tomcat 피크 | 8/200 (4%) | 7/200 (3.5%) |
| **PAID(실제 성공) 건수** | **16건 (1.4%)** | **0건 (0%)** |
| UNKNOWN_HOLD avg(DB 실측) | 2.976s | **1.580s** |

*control_traffic이 약간 높아진 건 폴링 경쟁 변동 범위 내로 보임(이전 측정들도 90~550ms 사이로 흔들렸음).

### 중요 - 트레이드오프가 숫자로 그대로 드러났다

**완료시간은 확실히 빨라졌다**(avg 4.11s→2.82s, p95 10.69s→5.74s, HOLD avg 2.98s→1.58s). 근데 그 대가로 **장애 시나리오에서 성공 건수가 16건→0건으로 떨어졌다.** 이유는 단순하다 - 우리 WireMock 장애 설정이 "항상 정확히 8초 뒤 성공"이고, TimeLimiter 타임아웃은 3초라서, **이 시나리오에서는 어떤 요청도 타임아웃 전에 끝날 수가 없다.** 8초 전부 다 끊긴다.

이게 바로 지난번에 설명한 "느리지만 성공했을 요청을 강제로 실패시킨다"는 트레이드오프가 실측으로 100% 확인된 것이다. 다만 이건 **우리 장애 시뮬레이션이 "항상 정확히 8초"라는 비현실적으로 고정된 값이라 더 극단적으로 보이는 것**이지, 실제 PG 지연은 보통 변동이 있어서(예: 1~5초 사이에서 흔들림) 3초 타임아웃이 모든 성공을 다 죽이진 않을 것이다. 이 트레이드오프의 크기를 더 현실적으로 보려면 장애 시나리오도 고정값 대신 지연 분포(예: lognormal median 4~5s)로 바꿔서 재측정해볼 필요가 있다.

**결론**: TimeLimiter는 "실패를 빠르고 예측 가능하게 만든다"는 목표는 확실히 달성했다. 다만 "타임아웃값(3초)을 얼마로 잡느냐"가 성공률과 응답속도 사이의 실제 비즈니스 트레이드오프이고, 지금 3초는 임의로 고른 값이라 - 실제 서비스라면 "PG가 느려도 어느 정도까지는 기다려서 성공시킬지" 기준을 비즈니스 쪽과 정해야 할 값이다.

## 장애 시나리오를 고정값 → 분포로 바꿔서 재측정 (2026-10-11 추가)

### 예상과 다르게 나온 부분 - 서킷브레이커의 "전부 아니면 전부" 효과

개별 호출만 보면 25%는 3초 밑으로 끝나서 성공할 "기회"가 있었는데, 실제 성공은 1128건 중 1건(0.09%)뿐이었다 - 25%보다 훨�십 적다. 원인은 **서킷브레이커는 개별 호출이 아니라 최근 호출들의 집계 패턴으로 열고 닫힌다**는 점이다. median이 4.5초면 대부분의 호출이 "느림(slow)" 기준(3초)을 넘기니까, 슬라이딩 윈도우가 금방 "느린 호출 비율 50% 초과"로 판단해서 **브레이커가 열려버리고, 그 뒤로는 실제로 몇 초 걸릴지와 상관없이 전부 즉시 차단(fast-fail)된다.** 즉 "이번엔 운좋게 3초 안에 끝났을 호출"조차 서킷브레이커가 열려있으면 Toss에 아예 요청을 보내보지도 못하고 차단당한다 - 개별 확률(25%)이 집계 판단(서킷브레이커) 때문에 거의 0%로 눌린 것.

**이건 서킷브레이커의 설계 의도상 당연한 결과다** - "가끔 운좋게 성공할 수 있다"는 가능성을 조금 포기하고 "전체 시스템을 안정적으로 보호한다"는 쪽을 택한 거니까. 다만 이번 수치로 "TimeLimiter + CircuitBreaker 조합이 생각보다 더 공격적으로 성공률을 깎는다"는 걸 체감할 수 있었다.

**완료시간은 세 시나리오 중 가장 좋다**(avg 1.87s, p95 3.89s) - median 지연 자체가 8초보다 낮고(4.5s) TimeLimiter가 그 위의 꼬리를 쳐내는 효과가 같이 작용한 결과.
